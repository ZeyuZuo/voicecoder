# Voice-Guided Frontend Coding Agent 技术调研结论

调研日期：2026-05-28

## 结论摘要

1. 前端/客户端建议使用 **Tauri 2 + React + TypeScript**，不要用 Flutter 做第一版。
2. 中国大陆语音识别服务建议优先使用 **腾讯云 ASR 实时说话人分离 WebSocket**；备选是 **科大讯飞实时语音转写/实时语音转写大模型**。
3. Codex 集成不要直接依赖闭源 Codex Desktop App。应优先调用 **开源 Codex CLI 的 `codex app-server` 协议**；简单自动化场景可用 `codex exec --json`；需要深度 UI 集成时再 clone `openai/codex` 研究 app-server schema 和源码。

## 1. 前端框架选择

### 推荐：Tauri 2 + React + TypeScript

这个产品本质上是本地桌面开发工具，需要：

- 选择本地项目目录；
- 读写文件、展示文件树；
- 启动/停止前端 dev server；
- 管理子进程，如 `npm run dev`、`codex app-server`；
- 内嵌 WebView 展示页面预览；
- 长时间运行，并实时接收 Codex/ASR 流式事件。

Tauri 适合这个形态：前端仍然用 Web 技术快速构建，后端用 Rust 负责本地能力、权限、进程和文件系统。Tauri 官方文件系统插件支持跨平台文件访问，也可以在 Rust 侧直接用 `std::fs` / `tokio::fs`。Tauri 还能通过插件/sidecar/命令机制管理本地进程。

React + TypeScript 适合做对话、文件树、diff、终端日志、预览面板这类复杂工具 UI，生态成熟，后续也便于迁移一部分 UI 到 Web。

### 为什么不优先 Flutter

Flutter 的桌面支持是正式能力，Windows/macOS/Linux 都可以编译，但这个项目的核心 UI 大量依赖 Web/IDE 生态：代码高亮、diff viewer、Monaco Editor、浏览器预览、WebSocket 流、Node 工具链联动。Flutter 可以做，但需要大量桥接和插件整合，尤其是桌面 WebView、终端、文件系统、子进程、代码编辑器体验，整体工程成本更高。

Flutter 更适合以移动端为核心、UI 强一致且不强依赖 Web 工具链的产品。这里第一版应优先把“本地编码闭环”跑通。

### Electron 的位置

Electron 也能做，而且 VS Code 这类 IDE 证明它适合复杂开发工具。Electron 的优势是 Node.js 子进程和文件系统能力非常直接，Chromium 行为一致；劣势是体积和资源占用更高，安全边界需要更谨慎。

如果团队完全不会 Rust，Electron + React + TypeScript 是务实备选。若团队可以接受 Rust，Tauri 更适合做长期本地工具。

## 2. 语音识别服务选择

### 推荐：腾讯云 ASR 实时说话人分离 WebSocket

需求里写了“实时语音转文字”和“支持多人语音识别”。这里的关键不是普通 ASR，而是实时说话人分离，也就是边说边出文字，同时标记是谁在说。

腾讯云有明确的“实时说话人分离（WebSocket）”接口，官方描述为在实时语音识别基础上增加声纹聚类能力，可实现“边说边出文字边识别角色”。它支持中文、英语、粤语、四川、陕西、河南、上海、湖南、湖北、安徽方言；音频格式支持 pcm/wav/opus/speex/silk/mp3/m4a/aac；返回 JSON；推荐按 200ms 音频包发送。

这和本项目的需求匹配度最高。

### 备选：科大讯飞实时语音转写/实时语音转写大模型

科大讯飞实时语音转写标准版支持持续音频流实时识别，参数 `roleType=2` 可开启角色分离，但官方标注“效果持续优化中”。实时语音转写大模型版本覆盖大量方言/语种，并有声纹分离相关能力，适合中文口音/方言复杂的场景。

如果实际测试中腾讯云的多人分离效果不稳定，应该并行接入讯飞做 A/B 测试。

### 不建议第一版选阿里云/百度作为主 ASR

阿里云百炼/DashScope 的 Qwen-ASR、Paraformer、Fun-ASR 实时识别能力很强，WebSocket 示例完整，但当前实时 ASR 文档重点是转写、VAD、情感识别、连接复用等；“实时多人说话人分离”不是它这页文档里的主接口。

百度智能云实时语音识别适合实时转写，也有音频文件转写的多说话人分离能力，但从公开产品页看，实时多人分离不如腾讯云这个接口直接。

### 可选本地方案：FunASR

如果未来要求“完全内网/不上云”，可以评估 FunASR。它是开源语音识别工具链，支持 ASR、VAD、标点、speaker diarization、实时 WebSocket 服务和 OpenAI-compatible transcription API。代价是要自己部署模型、GPU/CPU 性能调优、处理噪声和说话人聚类稳定性。

## 3. Codex CLI / Desktop App 如何结合

### 关键判断

不要试图调用闭源 Codex Desktop App。

Codex Desktop App 是产品壳和体验，闭源，不适合作为你自己的应用后端。真正可集成的是开源 `openai/codex` 仓库里的 CLI、SDK、app-server。

官方开源信息显示：

- Codex CLI 是开源主仓库；
- Codex SDK 在同一仓库；
- Codex App Server 在同一仓库；
- IDE extension 和 Codex Web 不是开源。

### 推荐集成方式：`codex app-server`

你的产品需要对话历史、审批、流式事件、命令执行、文件变更、用户输入请求等能力。这不是简单执行一次命令，所以首选 `codex app-server`。

`codex app-server` 是 Codex 用来支撑富客户端的协议，官方说明它适合嵌入自己的产品，支持认证、conversation history、approvals、streamed agent events。协议是 JSON-RPC 风格，默认 stdio JSONL，也支持 WebSocket/Unix socket。客户端流程大致是：

1. 桌面端启动 `codex app-server` 子进程；
2. 通过 stdio JSONL 发送 `initialize`；
3. `thread/start` 创建线程；
4. `turn/start` 发送 coding prompt；
5. 持续读取通知事件，更新 UI；
6. 遇到命令/文件修改审批请求时，在你的 UI 里展示并回传 accept/decline；
7. 根据 Codex 改动刷新文件树、diff 和页面预览。

本机验证结果：当前环境已有 `/home/zzy/.nvm/versions/node/v22.19.0/bin/codex`。`codex --help` 显示已支持 `exec`、`app-server`、`mcp-server`、`exec-server` 等子命令；`codex app-server --help` 显示默认 transport 是 `stdio://`，也支持 `ws://IP:PORT`、`unix://`，并支持 `generate-ts` 和 `generate-json-schema` 生成协议类型。

### 简化方式：`codex exec --json`

如果第一版只需要“需求确认后让 Codex 改代码，然后看结果”，可以先用：

```bash
codex exec --json --sandbox workspace-write "<coding prompt>"
```

`--json` 会让 stdout 变成 JSONL 事件流，包含 thread/turn、agent message、reasoning、command execution、file changes、plan updates 等事件。这个方案实现快，但交互能力不如 app-server，后面大概率还是要迁移。

本机验证结果：`codex exec --help` 中已有 `--json`、`--output-schema`、`--output-last-message`、`--cd`、`--sandbox` 等参数，足够作为 MVP 的第一次自动编码通道。

### 是否需要 clone Codex CLI 代码

需要，但不一定一开始就 fork。

建议顺序：

1. 第一阶段：把 `codex` 当外部二进制调用，先集成 `app-server` 或 `exec --json`。
2. 第二阶段：clone `openai/codex`，用 `codex app-server generate-ts --out ./schemas` 生成与你安装版本匹配的协议类型。
3. 第三阶段：阅读 `codex-rs/app-server`、`sdk`，补齐审批、线程恢复、错误处理、schema 版本兼容。
4. 只有当官方协议无法满足需求时，再考虑 fork；否则尽量不要维护 fork。

### 大陆访问风险

语音识别可以完全选国内云服务。但 Codex 本身仍然依赖 OpenAI/ChatGPT/Codex 服务。OpenAI 官方支持国家/地区列表没有把中国大陆列为受支持访问地区，官方也说明从不受支持地区访问 ChatGPT 或 OpenAI API 可能导致账号被阻止或暂停。

所以如果你的产品要求“全链路只在中国大陆可稳定访问且合规上线”，就不能把 OpenAI Codex 作为唯一编码后端。应设计一个 Agent Provider 层：

- `codex-provider`：面向个人/海外网络/内部试验；
- `qwen-coder-provider`：国内可用备选；
- `deepseek-coder-provider`：国内可用备选；
- `custom-cli-provider`：兼容其他本地 coding agent。

这样 UI、语音、需求澄清、项目预览都复用，编码智能体可替换。

## 推荐架构

```text
Tauri Desktop App
  ├─ React/TypeScript UI
  │   ├─ 项目选择 / 文件树 / 文件查看
  │   ├─ 对话与语音输入
  │   ├─ 需求状态面板
  │   ├─ Codex 事件流 / diff / 审批弹窗
  │   └─ 页面预览 WebView
  │
  ├─ Tauri Rust Backend
  │   ├─ 本地文件系统访问
  │   ├─ 项目 dev server 子进程管理
  │   ├─ Codex app-server 子进程管理
  │   ├─ ASR WebSocket 代理与鉴权
  │   └─ 本地状态存储
  │
  ├─ ASR Provider
  │   ├─ Tencent ASR realtime speaker diarization
  │   ├─ iFlytek realtime transcription
  │   └─ FunASR local optional
  │
  └─ Coding Agent Provider
      ├─ Codex app-server
      ├─ Codex exec --json
      └─ 国内 coding model/agent fallback
```

## MVP 建议

1. 先做 Tauri + React 桌面壳。
2. 接入本地项目选择、文件树、文件查看。
3. 接入腾讯云实时说话人分离，得到 `{speaker, text, timestamp}` 流。
4. 用普通 LLM 或规则先做需求结构化，不急着自动编码。
5. 用 `codex exec --json` 跑通一次“修改项目代码”的闭环。
6. 加 dev server 管理和预览刷新。
7. 迁移到 `codex app-server`，补审批、持续线程、恢复会话。

第一版可以优先在 Fedora 上开发和验证，但架构要按 Linux/Windows/macOS 跨平台设计：平台差异集中在 Tauri 后端和 `platform` 层，文件路径、子进程、凭证存储、麦克风权限、打包签名都不要散落在 UI 代码里。
