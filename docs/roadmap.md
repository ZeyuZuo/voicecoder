# Roadmap

目标：构建一个类似 Codex App 体验的本地桌面编码工作台。用户可以选择本地前端项目，通过文本或语音描述需求，系统持续澄清和整理需求，在确认后调用 Coding Agent 修改代码，并在同一个界面里查看文件、审查变更、打开预览和终端。

视觉与交互基准参考 `demo_images/demo1.png`、`demo_images/demo2.png`、`demo_images/demo3.png`：

- 左侧是固定导航和项目/对话列表。
- 中间是以对话和需求输入为核心的工作区。
- 右侧是随上下文变化的辅助工作区，包含文件、浏览器、审查、终端。
- 初始态保持干净克制，执行态展示 Codex 过程、变更摘要、代码和文件树。

## Phase 0：产品骨架与工程基础

目标：先把桌面应用工程、基础约束和主布局跑通，后续所有能力都落在同一套结构里。

交付物：

- Tauri 2 + React + TypeScript 项目骨架。
- 基础目录结构：`app/`、`docs/`、`experiments/`。
- 前端路由和桌面主窗口入口。
- 基础命令：开发启动、lint、typecheck、test。
- `.env.example`，只放变量名，不放真实密钥。
- 跨平台路径、文件访问、子进程管理的后端边界说明。

验收标准：

- 本机可以启动桌面开发窗口。
- 主窗口显示左侧导航、中间空态输入区、右侧工具入口区。
- 能跑通 lint/typecheck/test 中至少一组基础校验。
- README 或文档说明开发启动方式。

## Phase 1：App Shell 与空态首页

目标：复刻 demo 的核心体验骨架，让用户一打开应用就知道可以选择项目并发起需求。

交付物：

- 桌面应用窗口外壳区域和左侧浅灰导航栏。
- 顶部导航项：快速对话、搜索、技能、插件、自动化。
- 项目分组：展示最近项目、当前项目、项目下最近对话。
- 对话分组：展示不绑定项目的历史对话。
- 中间空态首页：
  - 标题文案：`我们应该在 voicecoder 中构建什么？`
  - 大输入框，支持多行文本。
  - 输入框工具条：添加、自动审查、模型、推理强度、发送。
  - 项目选择下拉：选择已有项目、添加新项目、不使用项目。
- 右侧工具入口空态：文件、浏览器、审查、终端四个入口。
- 本地状态持久化：最近项目、当前项目、最近会话、窗口布局。

验收标准：

- 无项目、选中项目、无聊天、有聊天四种侧边栏状态显示正确。
- 项目选择下拉可以打开系统目录选择器并记录项目。
- 输入区在空态居中，选择项目后显示项目名、本地模式、Git 分支等元信息。
- 窗口宽度变化时布局不重叠，最低宽度下保留主要操作。

## Phase 2：项目管理与文件工作区

目标：让应用具备“本地前端项目工作台”的基本能力。

交付物：

- 本地项目选择、移除、切换。
- 项目文件树读取，支持目录展开/收起、文件搜索、基础图标。
- 文件内容查看，支持 TypeScript、JavaScript、CSS、HTML、Markdown 等常见文件高亮。
- 右侧文件工作区：
  - 顶部 tab 展示已打开文件。
  - 面包屑展示文件路径。
  - 右侧文件树可折叠。
- 文件读取错误、权限错误、二进制文件、超大文件的提示。

验收标准：

- 选择一个前端项目后，右侧可以浏览项目文件并打开文件内容。
- 文件树不写死平台路径，所有路径都通过后端统一处理。
- 文件搜索能按文件名过滤。
- 打开多个文件时可以切换 tab，刷新后恢复最近打开状态。

## Phase 3：对话输入与需求状态机

目标：把“随便说一句需求”变成可确认、可执行、可追踪的结构化需求。

交付物：

- 文本对话流：用户消息、AI 回复、系统状态、错误状态。
- 流式 AI 回复展示。
- 结构化需求状态：
  - 目标
  - 页面/模块
  - 组件
  - 交互
  - 视觉约束
  - 技术约束
  - 待澄清问题
  - 验收标准
- 周期性需求总结。
- 主动追问机制。
- 需求确认卡片和 Coding Prompt 预览。
- coding prompt 可编辑、可确认、可取消。

验收标准：

- 文本输入会进入同一个需求状态机，而不是只追加普通聊天。
- 不明确需求不会直接触发编码。
- AI 能把当前需求总结成面向 Coding Agent 的 prompt。
- 用户确认前，界面明确显示“待澄清”或“待确认”状态。

## Phase 4：语音输入与多人转写

目标：把语音变成与文本同等的一等输入，支持多人需求讨论。

交付物：

- 主输入区录音按钮和录音状态。
- 腾讯云实时说话人分离 WebSocket 实验：`experiments/asr-tencent`。
- 音频采集、16kHz/16bit/mono PCM 转换、200ms 分片发送。
- 实时 partial/final 转写展示。
- 说话人、时间戳、句子分组。
- ASR Provider 抽象，腾讯云作为第一个实现。
- Mock ASR Provider，用于开发和测试。

验收标准：

- 可以用麦克风实时获得识别文本，并进入需求状态机。
- 可以解析并展示 `speaker_id`。
- 前端不接触腾讯云 SecretKey。
- 停止录音后 WebSocket 和音频资源正确释放。
- 鉴权失败、断线、麦克风权限失败有明确错误信息。

## Phase 5：Coding Agent MVP 集成

目标：先用简单可靠的方式跑通“确认需求后自动改代码”的第一条闭环。

交付物：

- `experiments/codex-exec` 实验。
- 使用 `codex exec --json --sandbox workspace-write --cd <project>`。
- JSONL 事件解析：
  - agent message
  - reasoning/plan
  - command execution
  - file change
  - final result
  - error
- 对话区展示执行过程和最终结果。
- 变更摘要卡片：文件数量、新增/删除行、关键文件列表。
- 原始事件日志留存，便于排查。

验收标准：

- 对测试前端项目可以发起一次代码修改。
- 用户能看到 Coding Agent 正在做什么、改了哪些文件、最后是否成功。
- 失败时保留原始事件日志。
- 第一版不默认自动修改用户真实重要项目，需要明确确认。

## Phase 6：审查、Diff 与回滚

目标：让用户在同一界面里看懂代码变更，并能决定接受、继续要求修改或回滚。

交付物：

- 审查工作区入口。
- 文件变更列表：新增、修改、删除、重命名。
- Diff Viewer，支持按文件查看。
- 变更摘要卡片嵌入对话流，和 demo 中“已编辑 N 个文件”类似。
- 操作按钮：
  - 继续要求修改
  - 打开文件
  - 审查
  - 回滚本轮变更
- Git 状态读取，显示当前分支和未提交变更。

验收标准：

- 每轮 Agent 结束后能看到明确的变更摘要。
- 点击文件变更可以打开对应 diff 或代码文件。
- 回滚只作用于本轮 Agent 变更，不误删用户原有改动。
- 对已有未提交改动的项目给出清晰风险提示。

## Phase 7：预览与终端反馈闭环

目标：把“改代码”升级为“改完马上看效果”。

交付物：

- 自动识别常见前端项目：Vite、Next.js、React Scripts 等。
- Dev server 启动、停止、重启。
- 右侧浏览器工作区，内嵌预览页面。
- 修改代码后自动刷新预览。
- 终端工作区，展示 dev server 日志和命令执行日志。
- 预览错误状态：端口占用、启动失败、依赖缺失、构建失败。

验收标准：

- 至少支持一种常见前端项目完整启动和预览。
- 预览失败时能展示端口、命令、stderr 摘要。
- 终端日志可以清空、复制、停止进程。
- Agent 改动后预览可以自动刷新或提示手动刷新。

## Phase 8：Codex App Server 深度集成

目标：从一次性 `codex exec` 升级为可持续多轮工作的富客户端协议。

交付物：

- `codex app-server` 子进程管理。
- 生成并维护协议类型。
- 支持线程、turn、流式事件、审批请求。
- 命令审批、文件修改审批、用户追问都回到主 UI。
- 会话恢复和历史记录。
- Coding Agent Provider 抽象，保留未来接入其他 coding agent 的能力。

验收标准：

- 同一项目可以持续多轮编码。
- 用户能在 UI 中批准或拒绝敏感操作。
- app-server 协议版本变化有兼容处理。
- UI 不绑定 Codex 私有实现，后续可以替换 provider。

## Phase 9：技能、自动化与可扩展能力

目标：把 demo 中的技能、插件、自动化从导航入口逐步变成可用能力。

交付物：

- 技能页：管理需求澄清、前端开发、审查、测试等预设能力。
- 插件页：预留本地 provider、工具和快捷命令扩展。
- 自动化页：周期性检查、定时任务、项目监控。
- 搜索页：搜索项目、会话、文件、变更和需求记录。
- 设置页：模型、ASR、Codex、隐私、路径、快捷键。

验收标准：

- 未完成能力不展示成可点击但无反馈的空按钮。
- 每个入口都有清晰空态和最小可用动作。
- 设置中的敏感信息不明文暴露在前端日志和页面中。

## Phase 10：跨平台打包与发布准备

目标：让产品从开发工具变成可以在主流桌面系统上安装使用的应用。

交付物：

- 主流桌面系统安装包。
- 跨平台凭证存储。
- 平台差异测试清单。
- 崩溃日志和诊断导出。
- 安装包不包含真实密钥或用户数据。

验收标准：

- 目标桌面平台至少完成一次本地打包验证。
- 麦克风权限、文件选择、子进程、路径处理在各平台可用。
- 不把任何真实密钥打进安装包。
- 用户可以导出诊断日志用于排查。

## MVP 范围

第一版 MVP 建议只做到 Phase 0 到 Phase 6 的核心路径：

```text
选择项目
  ↓
文本输入需求
  ↓
AI 澄清和总结
  ↓
用户确认 Coding Prompt
  ↓
Codex exec 修改测试项目
  ↓
展示变更摘要和 diff
```

语音、预览、app-server 可以并行实验，但不要阻塞第一条可用闭环。

## 关键风险

- 语音实时说话人分离的稳定性需要真实环境测试。
- Codex 在中国大陆网络和账号合规上存在不确定性，必须保留 provider 抽象。
- 本地文件修改存在误操作风险，第一版要优先做好确认、审查、回滚和日志。
- 前端工作台信息密度高，必须严格控制布局层级，避免把对话、文件、预览、终端堆成混乱面板。
